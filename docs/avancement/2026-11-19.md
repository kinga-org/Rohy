## Release 0.1.0 : plantage du scan sur Android
- Essai de l'APK `Rohy-android-0.1.0-test-signature.apk` sur le Galaxy S24 Ultra : l'app plante dès qu'on
  touche « Scanner le QR code » (`NullPointerException` dans le scanner ML Kit).
- Cause : la release est minifiée par R8 (mode complet). La règle fournie par ML Kit garde les classes
  `*Registrar` mais pas leur constructeur sans argument ; Firebase Components les crée par réflexion, donc
  ML Kit démarre sans ses composants. Le build debug (non minifié) n'a pas le problème.
- Correctif : règle `-keep … ComponentRegistrar { <init>(); }` dans `android/app/proguard-rules.pro`.
- Garde-fou : `scripts/check-r8-registrars.sh` lit le rapport R8 (`usage.txt`) et échoue si un constructeur
  de registrar a été retiré. Lancé par `scripts/check-android.sh` (CI et pre-push), qui construit maintenant
  aussi la release, et par l'action « Releases ».
- Vérifié sur le Samsung : APK de release corrigé installé, le scanner s'ouvre et analyse l'image.
- À faire : publier une 0.1.1 (la 0.1.0 brouillon a le bug).

## App Mac : design natif
- Retour du propriétaire : l'app Mac avec le thème Rohy (cartes vertes, Inter) ne fait pas native.
- Maquette dédiée « Rohy macOS — natif » (https://claude.ai/artifact/7VWrpCw2XEDyaH4Ze1tSRr) : panneau de
  la barre des menus façon menu système (connecté, survol + sous-menu « Oublier », aucun téléphone,
  erreur) et fenêtre d'association standard, en clair et sombre.
- Code, après essais sur le Mac du propriétaire :
  - d'abord un panneau SwiftUI (`MenuBarExtra` en style fenêtre) : macOS le redessinait avec des coins
    carrés dès que son contenu changeait de taille (le fond est dessiné par le système, hors de l'app) ;
  - remplacé par un vrai menu système (`NSStatusItem` + `NSMenu`), uniquement en éléments standard :
    titres de section, ligne d'état avec sous-titre (dernière activité, mise à jour toutes les 5 s menu
    ouvert), téléphones avec symbole `iphone.circle.fill` (28 pt, couleur d'accent si connecté) et
    sous-menu « Oublier ce téléphone… » (confirmation comme sur Android), section « Ce Mac », ⌘N, ⌘Q ;
  - fenêtre d'association en `NSWindow` (contenu SwiftUI) : QR, étapes, boutons standard « Copier le
    code » et « Terminé » ;
  - l'app démarre en AppKit pur (`main.swift`) : la scène SwiftUI vide gardée pour compiler ouvrait une
    fenêtre « Rohy Settings » après « Terminé » ;
  - Inter et le choix « Apparence » retirés de l'app Mac : elle suit le mode du système.
- Règle de parité du README mise à jour : mêmes fonctions et textes, apparence propre à chaque système.
- Vérifié par le propriétaire sur son Mac : menu arrondi et natif, association avec le Samsung, fenêtre
  fermée par « Terminé » sans fenêtre vide. Tests Swift et couverture OK.
- Écart avec la maquette : le menu est le menu standard du système (la maquette dessinait un panneau) ;
  la ligne du bas devient la section « Ce Mac » (même information, en deux lignes).

## Android 10 : plantage à l'association (Huawei P30 Pro)
- Essai de la 0.1.2 sur un Huawei P30 Pro (Android 10, avec Google Play) : l'app se ferme après le scan.
- Cause (journal adb) : `NoSuchMethodError` sur `URLDecoder.decode(String, Charset)`, méthode Java
  disponible seulement depuis Android 13, appelée en lisant le lien d'association (scan comme collage).
  Même problème pour `URLEncoder.encode(String, Charset)`. Le Samsung (Android 16) l'avait.
- Correctif : surcharges `decode(String, "UTF-8")` et `encode(String, "UTF-8")`, présentes partout.
- Garde-fou : Animal Sniffer sur le module `core` (signature Android 10 « gummy-bears-api-29 ») dans
  `scripts/check-android.sh` (CI et pre-push). Il signalait les deux appels avant le correctif. Android Lint
  ne vérifie pas les niveaux d'API d'un module Kotlin pur, essayé puis abandonné.
- Huawei / Honor : « Garder la connexion » ajoute « Lancement d'applications » (gestion manuelle) et
  « Verrouiller dans les apps récentes ». Huawei protège son écran de réglage : le bouton ouvre alors la
  page d'infos de l'app.
- Autorisations sur Android 10–12 : pas de fenêtre de demande pour les notifications (accordées à
  l'installation ; la demande n'existe qu'à partir d'Android 13). Comportement normal, expliqué au
  propriétaire.
- Vérifié sur le Huawei : association avec le Mac, service au premier plan, écran « Garder la connexion »
  et bouton « Ouvrir » sans plantage.

## Android Lint en CI sur l'app
- `:app:lintDebug` ajouté à `scripts/check-android.sh` (CI, pre-push) : les erreurs bloquent, dont `NewApi`
  (API plus récente que minSdk sans test de version). Preuve : un fichier jetable appelant
  `URLDecoder.decode(String, Charset)` fait échouer Lint (« Call requires API level 33 »).
- Lint a relevé, déjà corrigé : l'appel `startActivityAndCollapse(Intent)` de la tuile, protégé par un test de
  version mais non marqué ; les boutons « Ouvrir » (Samsung, Huawei) testaient l'écran avec
  `resolveActivity`, aveugle depuis Android 11 : ils essaient maintenant chaque écran l'un après l'autre.
- Avertissements restants (non bloquants) : dépendances à mettre à jour, `UseKtx`, sauvegarde, etc.
- Non vérifié sur téléphone : les boutons « Ouvrir » (téléphones débranchés).
